# 016. 캐시 없음 vs LRU 캐시 응답 시간

> 같은 LRU 캐시 1,000개를 붙였는데, 인기 상품에 요청이 몰리면 상품 페이지 2만 건이 209.6ms에서 77.5ms(2.70배)로 줄었고, 요청이 고르게 흩어지면 225.7ms에서 210.5ms(1.07배)에 그쳤다.

## 문제

자주 읽는 데이터 앞에 캐시를 두면 빨라진다고 한다. 그런데 얼마나 빨라질까?

```python
page = cache.get(product_id)
if page is None:                      # 미스: DB에서 읽고 캐시에 넣는다
    page = load_page(conn, product_id)
    cache.put(product_id, page)       # 꽉 차면 가장 오래 안 쓴 항목을 버린다 (LRU)
return page
```

히트면 DB를 건너뛰고, 미스면 DB 조회에 캐시 확인 비용까지 더한다. 캐시 조회가 공짜라고 쳐도 전체 시간은 미스 비율만큼만 남으니, 최대로 빨라지는 배율은 `1 / (1 - 히트율)`이다. 결국 몇 배 빨라지는지는 요청이 얼마나 몰리는지, 캐시가 몇 개를 들고 있는지에 달려 있다.

## 실험

- SQLite 파일 DB(WAL)에 상품 1만 개, 리뷰 30만 건(상품당 30건), `reviews(product_id, created_at)` 인덱스
- 상품 페이지 = 쿼리 2개: 상품 + 리뷰 수/평균 평점(`COUNT`, `AVG`), 최신 리뷰 3개
- 요청 2만 건을 두 가지 분포로 만들었다(시드 고정)
  - 인기 상품에 몰림: Zipf(s=1.0). 상위 100개가 요청의 53.4%, 상위 1,000개가 79.6%
  - 고르게 흩어짐: 상품을 균등하게 고름. 상위 1,000개가 23.5%
- 캐시 없음 / LRU 100개(상품의 1%) / LRU 1,000개(10%)를 비교. LRU는 `OrderedDict`로 직접 만든 프로세스 안 캐시이고, 요청 1건 시간은 캐시 확인부터 DB 조회, 캐시 저장까지 포함
- 같은 비교를 기본 키 조회 한 번(`SELECT id, name, price FROM products WHERE id = ?`)으로도 해서, DB 일이 더 작을 때와 비교
- 요청의 2%가 가격을 바꾸는 경우: 쓸 때 캐시를 그대로 두는 것과 DB에 쓴 뒤 캐시 키를 지우는 것을 비교하고, 캐시가 옛 가격을 돌려준 읽기를 셌다(한 스레드)
- `tracemalloc`으로 캐시에 페이지 100개, 1,000개를 넣었을 때 메모리를 쟀다
- 5번 돌려 지표별 중앙값. 캐시가 돌려준 응답이 모두 DB에서 바로 읽은 결과와 같은지, 키를 지우는 방식은 옛 가격이 0건인지 `assert`로 확인

```bash
python3 main.py
```

## 배운 점

- 캐시가 몇 배 빠르게 해 주는지는 히트율이 정한다. 같은 LRU 1,000개가 인기 상품에 몰린 요청에서는 히트 67.1%로 2.70배, 고르게 흩어진 요청에서는 히트 9.7%로 1.07배였다. 둘 다 `1 / (1 - 히트율)`(3.04배, 1.11배)을 넘지 못했다. 캐시를 붙이기 전에 요청이 얼마나 몰리는지부터 보는 게 맞다.
- 히트율이 낮으면 오히려 손해다. 요청이 흩어진 상태에서 LRU 100개는 히트 0.9%에 0.98배로, 캐시를 확인하고 넣는 비용만 더해졌다.
- 캐시는 p50을 낮추지만 p99는 거의 그대로다. 히트가 67.1%여도 나머지 요청은 미스라서 p50은 0.0104ms에서 0.0001ms로 내려갔는데 p99는 0.0132ms에서 0.0127ms였다. 느린 요청을 줄이려면 미스 자체(쿼리)를 빠르게 해야 한다.
- 캐시는 데이터를 한 벌 더 두는 것이라 바뀐 값을 따로 챙겨야 한다. 요청 2%가 가격을 바꿨을 뿐인데 무효화를 안 하면 읽기의 36.3%가 옛 가격을 받았다. 쓰기도 같은 인기 상품에 몰렸는데, 그 상품들은 캐시에서 잘 밀려나지 않아 옛 값이 오래 남았다. DB에 쓴 뒤 키를 지우자 0건이 됐고 히트율은 67.0%에서 65.9%로 조금 내려갔다. 다만 이건 한 스레드에서 잰 값이다. 여러 서버가 동시에 읽고 쓰면 지운 직후 다른 요청이 옛 값을 다시 넣을 수 있어서, TTL을 같이 두는 경우가 많다.
