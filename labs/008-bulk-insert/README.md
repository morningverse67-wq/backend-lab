# 008. 대량 INSERT: 무엇이 느리고, 어떻게 묶어야 할까

> 같은 1만 건인데 한 건마다 COMMIT 하면 1,948.84ms, 트랜잭션 하나로 묶으면 8.08ms(241.2배)였다. 느린 건 INSERT가 아니라 COMMIT이었다. 대신 하나로 묶으면 중간에 한 건만 실패해도 0건이 남는다.

## 문제

배치 작업에서 행을 이렇게 넣는 코드가 흔하다.

```python
for row in rows:
    conn.execute("INSERT INTO orders (...) VALUES (?, ?, ?, ?)", row)
    conn.commit()   # 또는 autocommit 모드라 문장마다 커밋
```

`executemany`나 여러 행을 한 문장에 넣는 `VALUES (...), (...), ...`로 바꾸면 빨라진다고들 한다. 그런데 실제로 시간을 잡아먹는 건 어디일까? 그리고 전부 한 트랜잭션으로 묶으면 무엇을 잃을까?

## 실험

- 주문 1만 건, `order_no`에 UNIQUE, `user_id`에 인덱스 1개 (SQLite **파일 DB**, 기본 설정 `journal_mode=delete`, `synchronous=FULL`, 시드 고정)
  - 메모리 DB는 저널 파일도 디스크 동기화(fsync)도 없어서 COMMIT 비용이 드러나지 않는다. 그래서 이번에는 임시 폴더에 파일 DB를 만들었다.
- 넣는 방법 4가지를 매번 빈 DB에서 측정하고, 결과(건수, 합계, 최소/최대 주문번호)가 같은지 `assert`로 확인
  1. 한 건씩 INSERT + 매번 COMMIT (autocommit)
  2. 한 건씩 INSERT, 트랜잭션 1개
  3. `executemany`, 트랜잭션 1개
  4. `VALUES (...), (...)` 500건씩 한 문장, 트랜잭션 1개
- 커밋 단위만 바꿔서 측정: 1 / 10 / 100 / 1,000 / 10,000건마다 COMMIT (`executemany`)
- 7,501번째 행에 중복 주문번호를 넣어 UNIQUE 위반을 일으키고, 커밋 단위별로 몇 건이 남는지 확인

```bash
python3 main.py
```

|---|---:|---:|---:|---:|

| `executemany`, 트랜잭션 1개 | 1 (`executemany`) | 1 | 6.52 | 299.1x |
| `VALUES` 500건씩, 트랜잭션 1개 | 20 | 1 | 6.27 | 310.8x |

| 1 | 10,000 | 1,917.89 | 1.0x |

| 몇 건마다 COMMIT | 남은 행 |
|---:|---:|
| 10,000 (전부 한 트랜잭션) | 0 |

## 배운 점

- 이 실험에서 느린 건 INSERT가 아니라 **COMMIT**이었다. 같은 1만 번의 INSERT도 COMMIT을 1만 번에서 1번으로 줄이자 1,948.84ms → 8.08ms가 됐다. 커밋마다 저널을 쓰고 디스크에 확실히 기록될 때까지 기다리기 때문이다.
- 트랜잭션을 묶은 뒤에는 `executemany`(6.52ms)나 여러 행 `VALUES`(6.27ms)의 추가 이득이 작았다. 다만 SQLite는 같은 프로세스 안에서 도는 DB라 네트워크 왕복이 없다. MySQL처럼 서버와 통신하는 DB는 문장마다 왕복이 생기므로 묶어 보내는 효과가 더 클 것이다(여기서는 재지 않음, 왕복 비용은 [lab 001](../001-n-plus-one) 참고).
- 커밋 단위는 크게 잡을수록 빨라지지만 금방 평평해진다. 1,000건 단위(10.16ms)만 돼도 전부 하나로 묶은 것(6.63ms)과 차이가 작았다.
- 전부 한 트랜잭션이 항상 정답은 아니다. 7,501번째 행 하나 때문에 1만 건이 모두 롤백돼 0건이 남았다. 반대로 1,000건 단위는 7,000건이 남으니, 다시 돌릴 때 어디서부터 이어 넣을지(또는 중복을 무시할지) 정해 둬야 한다. 트랜잭션이 길어지면 그동안 락을 오래 잡는 문제도 있다. "전부 성공 아니면 전부 취소"가 필요한 데이터인지, 이어서 넣어도 되는 데이터인지에 따라 단위를 고른다.
