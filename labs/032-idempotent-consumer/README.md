# 032. 멱등 소비자(inbox): 두 번 온 이벤트를 한 번만 반영하기

> 포인트 적립 이벤트 1만 건을 소비자가 처리했다. 브로커가 3%를 다시 보내고 소비자가 반영 직후 2% 확률로 죽게 하자, 그냥 반영은 548건을 더 적립했다. 반영한 뒤 이벤트 id를 따로 기록하는 방식도 223건을 더 적립했다. id 기록(inbox)과 반영을 한 트랜잭션에 넣자 초과 적립이 0이 됐다.

## 문제

[031](../031-transactional-outbox)에서 outbox는 유실을 0으로 만드는 대신 이벤트를 최소 한 번(at-least-once) 보냈다. 같은 이벤트가 두 번 오면 소비자는 포인트를 두 번 적립한다. 흔한 해법은 "처리한 이벤트 id를 기록해 두고 본 것은 건너뛰기"다. 그런데 기록을 언제, 어떤 트랜잭션에서 하느냐에 따라 결과가 달라진다. 세 방식에서 적립이 몇 번 더 됐는지 센다.

## 실험

- 이벤트 10,000건, 한 건에 100포인트. SQLite(메모리), 표준 라이브러리만 사용
- 브로커 재전송 3%, 소비자가 반영 뒤·ack 전에 죽기 2% (`random.Random(32)`로 고정). 죽으면 그 이벤트는 다시 온다
- 그냥 반영: 받을 때마다 포인트 증가
- 반영 후 id 기록: `inbox`에 id가 있으면 건너뜀. 없으면 반영 커밋 → (죽을 수 있음) → id 기록 커밋
- inbox + 반영 한 트랜잭션: `inbox`(id가 기본키)에 넣기와 포인트 증가를 한 트랜잭션에. 이미 있으면 기본키 충돌로 건너뜀

```bash
python3 main.py
```

## 결과

| 방식 | 받은 횟수 | 반영 횟수 | 초과 반영 |
|---|---:|---:|---:|
| 그냥 반영 | 10,548 | 10,548 | 548 |
| 반영 후 id 기록(따로 커밋) | 10,533 | 10,223 | 223 |
| inbox + 반영 한 트랜잭션 | 10,533 | 10,000 | 0 |

<sub>Python 3.13.12, macOS arm64. 시드가 고정이라 같은 코드에서 매번 같은 수가 나옴. 방식마다 난수를 쓰는 순서가 달라 받은 횟수가 조금 다름. 재전송·장애 확률은 실험용 값.</sub>

## 배운 점

- 중복을 거르지 않으면 받은 만큼 반영된다. 재전송과 재시작으로 548건(5.48%)이 더 적립됐다.
- id를 기록해도, 반영과 기록이 서로 다른 커밋이면 그 사이에 죽은 223건이 다시 적립됐다. 브로커 재전송은 걸렀지만 소비자 자신의 재시작은 못 거른 것이다.
- id 기록과 반영을 한 트랜잭션에 넣으면 둘이 같이 커밋되거나 같이 롤백된다. 기본키 충돌이 "이미 처리함"을 알려 주므로 따로 조회할 필요도 없다. 초과 반영이 0이었다.
- 반영 대상이 같은 DB에 있어야 이 방법이 된다. 외부 결제 API처럼 다른 시스템을 호출한다면 그쪽에 멱등성 키를 넘겨야 한다([014](../014-idempotency-key)).
- `inbox` 테이블은 계속 커지므로, 브로커가 다시 보낼 수 있는 기간이 지난 행은 정리해야 한다. 이 실험에서는 정리를 다루지 않았다.
