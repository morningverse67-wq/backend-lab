# 014. 멱등성 키로 중복 결제 요청 막기

> 주문 200건마다 같은 결제 요청이 3번씩 동시에 들어왔다. 키를 먼저 조회하고 결제하는 코드는 DB에 결제 200건만 남겼는데, 결제 대행사(PG)에는 결제가 599번 나갔다. 결제 전에 키부터 저장하자 200번이 됐다.

## 문제

결제 요청은 한 번만 오지 않는다. 버튼을 두 번 누르기도 하고, 서버는 이미 결제를 끝냈는데 응답이 늦어 클라이언트가 타임아웃 뒤 다시 보내기도 한다. 그래서 클라이언트가 결제 하나마다 키를 만들어 보내고, 서버는 같은 키를 한 번만 처리한다(멱등성 키).

흔한 첫 구현은 "키가 있는지 먼저 보고, 없으면 처리"다.

```python
row = db.execute("SELECT payment_id FROM idempotency_keys WHERE key = ?", (key,)).fetchone()
if row:
    return row[0]              # 이미 처리한 요청
pg.charge(order_id, amount)    # 같은 키 요청 두 개가 둘 다 여기까지 온다
db.execute("INSERT INTO idempotency_keys ...")   # UNIQUE라 하나는 실패하지만 결제는 이미 나갔다
```

결제는 DB 밖(PG)에서 일어나서 `ROLLBACK`으로 되돌릴 수 없다. 이번 lab은 DB 행 수가 아니라 PG에 나간 결제 횟수를 센다.

## 실험

- SQLite 파일 DB(WAL). `payments` 테이블과 `idempotency_keys(key PRIMARY KEY, request_hash, status, payment_id)` 테이블
- 가짜 PG: 결제 한 번에 2ms 걸리고, 결제 내역은 DB와 따로 기록한다(DB를 롤백해도 남는다)
- 비교한 서버 처리 방식
  - 키 없음: 요청마다 결제하고 `payments`에 INSERT
  - 먼저 조회 후 결제: 키를 `SELECT`로 확인하고 없으면 결제한 뒤, 결제 행과 키를 트랜잭션 하나로 INSERT. 키 UNIQUE 위반이면 롤백하고 저장된 응답을 돌려준다
  - 키 먼저 저장: `INSERT ... ON CONFLICT(key) DO NOTHING RETURNING key`로 키를 `processing` 상태로 먼저 넣는다. 넣은 요청만 결제하고 `done`으로 바꾼다. 못 넣은 요청은 저장된 응답을 받거나, 아직 처리 중이면 409를 받고 3ms 뒤 같은 키로 다시 보낸다
- 1부, 동시 중복: 주문 200건 x 같은 요청 3번, 8스레드. 같은 주문의 요청 3개가 거의 동시에 처리되도록 큐에 붙여 넣었다. 3번 돌려 지표별 중앙값
- 2부, 응답 유실 후 재시도(키 먼저 저장 방식): 첫 요청은 서버에서 성공했지만 클라이언트가 응답을 못 받아 한 번 더 보낸다. 재시도에 같은 키를 쓰는 경우와 시도마다 새 키를 만드는 경우. 3번 돌려 중앙값. 같은 키에 금액만 다른 요청, PG가 한 번 실패했을 때 키를 지우는 경우와 안 지우는 경우도 확인
- 3부, 대가: 중복 없는 주문 300건을 하나씩 처리할 때 요청 1건 시간. PG 0ms와 2ms, 5번 돌려 중앙값
- 키 먼저 저장 방식이 PG 결제 200번·DB 행 200건이고 같은 주문의 응답이 모두 같은지, 시도마다 새 키면 400번인지 `assert`로 확인

```bash
python3 main.py
```

## 배운 점

- 먼저 조회하는 방식은 DB만 보면 멀쩡하다. UNIQUE 제약 덕분에 결제 행은 정확히 200건이고 같은 주문의 응답도 모두 같았다. 그런데 PG 결제는 599번이었다. 같은 키 요청 600개 중 599개가 "아직 없음"을 본 뒤 결제까지 갔고, UNIQUE는 그다음 INSERT에서야 막았다. 외부 호출이 끼면 DB 제약은 마지막 줄에서만 지켜 준다.
- 결제 전에 키를 먼저 저장하면 DB의 UNIQUE가 "누가 처리할지"를 정해 준다. 키를 넣은 요청 하나만 결제했고 PG 결제는 200번, 나머지는 저장된 응답이나 409를 받았다. 대신 같은 키 요청은 기다리는 409가 426번 생겨서 전체 시간이 545.9ms에서 958.1ms로 늘었다. 중복 요청을 정상 처리 속도로 돌려주는 게 목표가 아니라 한 번만 결제하는 게 목표다.
- 키는 클라이언트가 결제 하나마다 한 번 만들어야 한다. 재시도에 같은 키를 쓰면 저장된 응답을 0.041ms 만에 돌려줬지만, 시도마다 새 키를 만들면 서버 입장에서는 다른 요청이라 200건 모두 두 번 결제됐다(400번). 같은 키로 금액이 다른 요청이 오면 저장된 응답을 돌려주지 말고 거절해야 한다(422). 요청 내용 해시를 같이 저장한 이유다.
- 키를 저장한 뒤 실패하면 그 키를 어떻게 할지 정해야 한다. PG 실패 뒤 키를 지우자 다음 재시도가 정상 결제됐고, `processing`으로 두자 재시도 5번이 모두 409였다. 서버가 처리 중에 죽어도 같은 상태가 남으니, 실제로는 만료 시간이나 상태 확인 작업이 필요하다(이 lab에서는 재지 않았다). 반대로 PG가 실제로는 결제했는데 응답만 실패한 경우 키를 지우면 다시 결제될 수 있어서, PG가 제공하는 멱등성 키나 결제 조회로 확인하는 편이 안전하다.
- 대가는 크지 않았다. 키 저장과 완료 표시로 쓰기가 두 번 늘어 DB 작업만 보면 요청당 0.043ms에서 0.191ms(4.48배)가 됐지만, PG 호출 2ms를 넣으면 1.22배였다. 다만 키 테이블은 요청마다 행이 쌓이므로 보관 기간을 정해 지워야 한다. 조회처럼 원래 여러 번 해도 결과가 같은 요청에는 키가 필요 없다.
