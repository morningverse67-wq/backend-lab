# 017. Cache stampede와 single-flight

> 캐시가 만료된 순간 같은 키로 요청 32개가 동시에 들어오자 같은 집계 쿼리가 32번 돌았고, 다 끝나는 데 140.6ms가 걸렸다. 한 요청만 쿼리하고 나머지는 기다리게(single-flight) 하자 쿼리 1번, 16.6ms였다.

## 문제

비싼 결과를 캐시에 두고 TTL이 지나면 다시 읽는 흔한 코드다.

```python
ranking = cache.get(category)
if ranking is None:                       # 만료됐으면
    ranking = conn.execute(RANK_SQL, (category,)).fetchall()   # 리뷰 30만 건 집계
    cache.set(category, ranking, ttl=60)
return ranking
```

요청이 하나씩 오면 문제없다. 그런데 인기 있는 키가 만료되는 순간 요청이 몰리면, 그 요청들은 모두 미스를 보고 모두 같은 쿼리를 DB에 보낸다. 캐시가 막아 주던 부하가 한꺼번에 DB로 쏟아지는 것을 cache stampede(또는 thundering herd)라고 한다.

## 실험

- SQLite 파일 DB(WAL)에 상품 1만 개(카테고리 100개), 리뷰 30만 건. 카테고리별 평균 평점 상위 10개 랭킹을 캐시한다. `category`에 인덱스가 없어 쿼리 1번이 리뷰 30만 건을 훑는다(단독 19.4ms)
- 캐시 항목을 강제로 만료시키고, 바로 동시 요청 N개(8개, 32개)를 `threading.Barrier`로 한꺼번에 보낸다. 이걸 10번 반복한다. 스레드마다 SQLite 연결을 따로 쓴다
- 세 가지를 비교했다
  - 보호 없음: 미스를 본 요청이 각자 쿼리한다
  - single-flight: 키마다 처음 미스를 본 요청 하나만 쿼리하고, 나머지는 그 결과를 기다렸다가 같이 받는다(`threading.Event`)
  - stale-while-revalidate(SWR): 만료된 값을 바로 돌려주고, 백그라운드 스레드 하나가 새 값을 읽어 채운다
- 같은 N개 요청이 서로 다른 카테고리 N개로 흩어진 경우도 쟀다. 합칠 같은 키가 없을 때다
- 요청 1건 시간(p50/p99), 만료 1번에 몰린 요청이 모두 끝나는 시간(이하 끝나는 시간), DB 쿼리 수를 셌다. 3번 돌려 지표별 중앙값. 모든 응답이 쿼리 결과와 같은지 `assert`로 확인

```bash
python3 main.py
```

## 배운 점

- 동시에 몰리는 미스는 DB 일을 그대로 곱한다. 같은 키에 32개가 오자 쿼리가 만료 1번마다 32번 돌았고, 서로 CPU를 나눠 쓰느라 단독 19.4ms였던 쿼리가 p99 161.63ms까지 늘었다. 8개일 때(p99 69.72ms)보다 훨씬 나빠서, 몰리는 요청이 많을수록 피해가 커진다.
- single-flight는 같은 키의 미스를 하나로 합친다. 32개여도 쿼리는 1번, 끝나는 시간은 140.6ms → 16.6ms(8.5배)였다. 기다린 요청도 쿼리 1번 시간만큼만 기다린다.
- 합칠 게 없으면 single-flight는 이득이 없다. 요청이 키 32개로 흩어지면 쿼리는 그대로 320번이고 끝나는 시간은 103.5ms → 114.3ms(0.91배)로 오히려 조금 느렸다. stampede는 인기 키 하나가 만료될 때 생기는 문제라 그 키에만 걸면 된다.
- SWR은 아무도 기다리지 않게 하는 대신 만료된 값을 준다. 같은 키 32개에서 p99 0.47ms였지만 그 만료 순간의 응답 320건이 모두 만료된 값이었다. 랭킹처럼 조금 늦어도 되는 데이터에 맞고, 재고나 가격처럼 바로 맞아야 하는 값에는 맞지 않는다. 또 이 실험에서는 서버 한 대 안의 락으로 합쳤다. 서버가 여러 대면 서버마다 1번씩 쿼리하므로, 그것도 막으려면 분산 락 같은 별도 장치가 필요하다(재지 않음).
