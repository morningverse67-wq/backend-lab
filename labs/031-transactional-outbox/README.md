# 031. Transactional outbox: DB 저장과 메시지 발행 같이 하기

> 주문 1만 건을 저장하고 '주문 생성' 이벤트를 보냈다. 두 단계 사이에서 2% 확률로 죽게 하자, 커밋 후 발행은 저장된 주문 197건의 이벤트를 잃었고, 발행 후 커밋은 저장되지 않은 주문 317건의 이벤트를 내보냈다. 주문과 이벤트를 한 트랜잭션에 넣는 outbox는 유실·유령이 0이었지만 216건이 두 번 나갔고, 소비자가 이벤트 id로 걸러서 9,905건만 처리했다.

## 문제

주문을 DB에 저장하고, 결제·알림 서비스가 알 수 있게 메시지 브로커에 이벤트를 보낸다고 하자.

```python
db.commit(order)
broker.publish(order_created)
```

DB와 브로커는 서로 다른 시스템이라 한 트랜잭션으로 묶이지 않는다. 두 줄 사이에서 프로세스가 죽거나 네트워크가 끊기면 한쪽만 반영된다. 순서를 바꿔도 반대쪽 문제가 생긴다. Transactional outbox는 이벤트를 같은 DB의 `outbox` 테이블에 주문과 함께 저장하고, 별도 릴레이가 그 테이블을 읽어 브로커로 보낸다. 세 방식에서 무엇이 어긋나는지 센다.

## 실험

- 주문 10,000건, SQLite(메모리), 브로커는 파이썬 리스트. 표준 라이브러리만 사용
- 장애: DB 커밋 실패 1%, 두 단계 사이에서 죽기 2% (`random.Random(31)`로 고정)
- 커밋 후 발행: 커밋 → (죽을 수 있음) → 발행
- 발행 후 커밋: 발행 → (죽을 수 있음) → 커밋
- outbox: 주문 + outbox 행을 한 트랜잭션에 커밋. 릴레이가 `sent=0` 행을 보내고 `sent=1`로 표시. 보낸 뒤 표시 전에 죽으면 다음 회차에 다시 보냄
- 유실: 저장됐는데 이벤트가 없음 / 유령: 이벤트는 나갔는데 주문이 없음 / 중복: 같은 이벤트가 두 번 이상

```bash
python3 main.py
```

## 결과

| 방식 | 저장된 주문 | 발행된 이벤트 | 유실 | 유령 | 중복 |
|---|---:|---:|---:|---:|---:|
| 커밋 후 발행 | 9,889 | 9,692 | 197 | 0 | 0 |
| 발행 후 커밋 | 9,683 | 10,000 | 0 | 317 | 0 |
| outbox + 릴레이 (3회 돎) | 9,905 | 10,121 | 0 | 0 | 216 |

```text
outbox 소비자: 중복 무시 없이 10,121번 처리, 이벤트 id로 거르면 9,905번 처리
```

<sub>Python 3.13.12, macOS arm64. 시드가 고정이라 같은 코드에서 매번 같은 수가 나옴. 장애 확률은 실험용으로 정한 값이고 실제 서비스의 장애율이 아님.</sub>

## 배운 점

- 커밋 후 발행은 죽는 순간 저장된 주문의 이벤트가 사라진다(197건). 결제·알림 쪽은 그 주문이 있는 줄 모른다.
- 발행 후 커밋은 반대로 DB에 없는 주문의 이벤트가 나간다(317건). 커밋 실패까지 겹쳐서 유실보다 많았다. 순서를 바꾸는 것만으로는 둘 중 하나를 고르는 것밖에 안 된다.
- outbox는 주문과 이벤트가 같이 커밋되거나 같이 빠지므로 유실·유령이 0이다. 대신 릴레이가 보낸 뒤 표시하기 전에 죽으면 다시 보내서 **최소 한 번(at-least-once)** 전달이 된다. 이 실험에서 216건이 두 번 나갔다.
- 그래서 outbox는 소비자 쪽 멱등 처리와 짝이다. 이벤트 id를 기록해 두고 본 것은 건너뛰자 처리 횟수가 저장된 주문 수(9,905)와 같아졌다. (멱등성 키는 [014](../014-idempotency-key) 참고)
- 이 실험은 릴레이가 결국 끝까지 돈다고 가정했다. 실제로는 릴레이 지연만큼 이벤트가 늦게 나가고, outbox 테이블 정리도 따로 해야 한다.
