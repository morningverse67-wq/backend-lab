# 012. 재고 차감, 원자적 UPDATE 한 줄이면 될까

> 재고 100개인 상품에 주문 400건이 동시에 들어왔다. 재고를 읽고 앱에서 검사한 뒤 쓰는 코드는 400개를 모두 팔았고, 재고는 50개가 남았다. `UPDATE ... SET qty = qty - 1 WHERE qty > 0` 한 줄은 정확히 100개만 팔았다.

## 문제

재고 차감을 이렇게 짜는 경우가 많다.

```sql
SELECT qty FROM items WHERE id = 1;           -- 1개 남음
-- 애플리케이션에서 qty > 0 검사, 주문 검증 같은 작업
UPDATE items SET qty = 0 WHERE id = 1;        -- 읽은 값 - 1을 씀
```

두 요청이 같은 "1개 남음"을 읽으면 둘 다 판다. [lab 010](../010-lost-update-optimistic-lock)의 lost update에 "재고보다 더 파는" 문제가 겹친다.
검사와 차감을 DB 한 문장 안에서 하면 읽고 쓰는 사이의 틈이 없어진다.

```sql
UPDATE items SET qty = qty - 1 WHERE id = 1 AND qty > 0;   -- 바뀐 행이 1이면 판매 성공, 0이면 품절
```

궁금한 것은 세 가지다. 실제로 얼마나 더 파는가, 락([lab 010](../010-lost-update-optimistic-lock), [lab 011](../011-pessimistic-lock))과 비교해 얼마나 빠른가, 그리고 이 한 줄로 안 되는 경우는 언제인가.

## 실험

- SQLite 파일 DB(WAL 모드), 8스레드가 같은 상품을 1개씩 주문한다
- 주문마다 1ms 앱 작업(주문 검증 같은 일을 흉내 낸 것)을 한다. 읽고-쓰기 방식은 `SELECT`와 `UPDATE` 사이에, 원자적 UPDATE는 `UPDATE` 전에 락 밖에서 한다
- 비교한 방법
  - 읽고-쓰기: `SELECT` → `qty > 0` 검사 → `SET qty = ?`(읽은 값 - 1)
  - 읽고 검사 + `qty - 1`: 검사는 앱에서, 차감만 `SET qty = qty - 1`
  - 원자적 UPDATE: `SET qty = qty - 1 WHERE id = ? AND qty > 0`, 바뀐 행 수로 성공 판단
  - 낙관적 락: `WHERE version = ?`, 바뀐 행이 0이면 다시 읽고 재시도 (lab 010과 같음)
  - 행 락(비관적 락): 행마다 락을 두고 먼저 온 순서대로 넘겨줌 (lab 011과 같음, SQLite에 `FOR UPDATE`가 없어서 흉내 냄)
- 경우 1: 재고 100개, 주문 400건(품절까지). 팔린 수량과 남은 재고를 본다
- 경우 2: 재고 800개, 주문 800건(모두 성공). 전체 시간을 본다
- 경우 3: 장바구니. 주문마다 상품 A(재고 100)와 B(재고 30)를 1개씩 사야 성공. 원자적 UPDATE 두 개를 하나씩 커밋할 때와 트랜잭션 하나로 묶고 실패하면 `ROLLBACK`할 때를 비교
- 경우 1, 2는 3번 돌려 지표별 중앙값을 적었다. 원자적 UPDATE, 낙관적 락, 행 락은 매번 정확히 재고만큼 팔고 재고 0이 남는지, 경우 3은 남은 재고가 기대값과 같은지 `assert`로 확인

```bash
python3 main.py
```

## 배운 점

- 읽고-쓰기는 에러 없이 재고보다 많이 판다. 8스레드가 같은 재고를 읽고 같은 값을 써서, 400건이 모두 팔렸는데 재고는 50개밖에 줄지 않았다(300개 초과 판매). 재고가 충분한 경우 2에서도 800개를 팔고 재고는 700개가 남았다. 품절이 나지 않으면 틀린 줄도 모른다.
- 차감만 `qty - 1`로 바꾸면 절반만 고쳐진다. 숫자는 맞게 줄지만 검사는 여전히 옛 값으로 해서, 마지막 1개를 8스레드 중 여러 개가 같이 보고 107개를 팔았다. 재고는 -7이 됐고 3회 모두 같았다. 검사와 차감이 같은 문장 안에 있어야 한다.
- 원자적 UPDATE는 재시도도 락 코드도 없이 정확히 100개만 팔았다. 앱 작업을 락 밖에서 할 수 있어서, 주문 800건이 634.9ms로 낙관적 락(1,375.6ms, 재시도 2,927번)이나 행 락(1,379.7ms)보다 2.17배 빨랐다. 다만 품절이 빨리 나는 경우 1에서는 178.4ms vs 180.2ms로 차이가 없었다. 행 락도 품절 뒤에는 바로 실패하기 때문이다. 경우 2에서 원자적 UPDATE가 틀린 방법들과 비슷한 시간(587.6~645.4ms)인 것은 SQLite가 쓰기를 파일 단위로 하나씩만 받아서 쓰기 자체가 바닥 시간이 된 것으로 보인다. 다른 DB에서는 다를 수 있다.
- 한 줄로 안 되는 경우도 있다. 상품 두 개를 같이 사야 하는 주문에서 원자적 UPDATE를 하나씩 커밋하면, A를 뺀 뒤 B가 품절이라 주문이 실패해도 A는 이미 빠져 있다. 30건만 팔렸는데 A 재고 70개가 사라졌다. 트랜잭션으로 묶고 실패하면 `ROLLBACK`해야 한다(여러 행을 잠그는 순서는 데드락과 이어져서 뒤 lab에서 다룬다). 1인당 구매 제한처럼 다른 테이블을 봐야 하는 규칙도 `WHERE` 한 줄에 안 들어가서 락이 필요하다.
- 정리하면, 재고처럼 한 행의 숫자를 조건부로 줄이는 일은 원자적 UPDATE가 먼저다. 바뀐 행 수를 꼭 확인하고, 여러 행이 함께 바뀌어야 하면 트랜잭션으로 묶는다. 읽은 값으로 복잡한 판단을 해야 할 때 낙관적 락이나 비관적 락을 쓴다.
