# 027. 정렬된 두 리스트 병합 vs 해시 조인

> 이미 정렬된 입력에서는 병합 조인이 195.8ms, 해시 조인이 57.0ms였다. 두 리스트를 먼저 정렬해야 하는 경우까지 재면 병합 조인은 200.2ms였다. 이 데이터에서는 해시 조인이 빨랐지만, 입력이 이미 정렬돼 있거나 순서대로 흘려 보내야 할 때는 병합 조인이 해시 테이블 메모리를 만들지 않는 장점이 있다.

## 문제

두 테이블을 join할 때 데이터베이스는 어떤 방법을 고를까? 대표적으로 한쪽을 해시 테이블로 만들고 다른 쪽을 조회하는 **해시 조인**, 두 입력을 정렬해 같은 키끼리 한 번씩 훑는 **병합 조인**이 있다.

입력을 훑는 기본 비용은 두 방식 모두 O(N+M)이고, 결과가 R행이면 두 방식 모두 결과 생성에 O(R)이 더 든다. 따라서 전체 시간은 결과 출력까지 포함해 O(N+M+R)로 봐야 한다. 하지만 해시 조인은 한쪽 입력을 메모리에 인덱싱하고, 병합 조인은 양쪽이 이미 정렬되어 있어야 한다. 정렬이 필요하면 그 비용도 포함해야 한다. 같은 데이터와 결과를 두 방식으로 조인하고, 입력 정렬 여부가 시간과 Python 할당 메모리에 미치는 차이를 잰다.

## 실험

- 왼쪽 80,000행, 오른쪽 20,000행, join key 범위 0~9,999의 결정적 입력을 만든다. 양쪽에 중복 키가 있어 결과는 일대다·다대다를 포함한다.
- **해시 조인**은 오른쪽을 `dict[key] -> rows`로 인덱싱한 뒤 왼쪽을 훑는다.
- **병합 조인**은 두 입력을 키 순서로 훑고, 같은 키가 연속으로 여러 번 나오면 해당 구간의 조합을 결과로 낸다.
- 두 경우를 비교한다: 키가 이미 정렬된 입력, 그리고 원본 입력을 그대로 받아 병합 조인 쪽에서 정렬 비용까지 부담하는 경우. 해시 조인은 두 경우 모두 입력을 정렬하지 않는다.
- 결과 행 수와 checksum이 두 방식·두 조건에서 같은지 검사한다. 각 측정은 별도 프로세스에서 실행하며, 입력 생성은 측정 밖이다.
- 시간과 `tracemalloc` 최대 할당량을 각각 5회 재고 중앙값을 출력한다. `tracemalloc` 값은 전체 프로세스 RSS가 아니다.

```bash
python3 main.py
```

## 결과

| 입력 조건 | 방법 | 시간 중앙값 (ms) | tracemalloc 최대치 (MB) |
|---|---|---:|---:|
| 이미 정렬됨 | 병합 조인 | 195.8 | 10.2 |
| 이미 정렬됨 | 해시 조인 | 57.0 | 11.3 |
| 원본 입력, 병합 쪽 정렬 포함 | 병합 조인 | 200.2 | 11.0 |
| 원본 입력 | 해시 조인 | 52.2 | 11.3 |

양쪽 방법 모두 159,975개 결과 행, checksum `213,040,298,565`를 만들었다. 중복 키가 있으므로 결과 행 수는 입력 행 수의 합보다 많다. 이 실험의 Python 구현에서는 해시 조인이 더 빨랐고, 병합 조인은 이미 정렬된 입력에서도 더 느렸다. 실행 시간은 입력 크기·키 분포·Python 구현·환경에 따라 달라진다. `tracemalloc` 최대치에는 공통 결과 리스트가 포함되므로, 이 표만으로 운영 DB의 전체 메모리 사용량을 추정할 수는 없다.

<sub>Python 3.13.12, macOS arm64. 시간·tracemalloc 최대치: 각 방법·조건별 별도 프로세스 5회 중앙값. 입력은 고정 seed로 생성.</sub>

## 배운 점

- **정렬이 끝난 입력을 순차 처리**한다면 병합 조인은 키 순서대로 읽으며 처리할 수 있다. 정렬된 파일이나 인덱스가 이미 있거나 결과를 순서대로 스트리밍할 때 선택지가 된다.
- 해시 조인은 보통 한쪽 입력을 해시 테이블에 올리는 비용이 들지만, 입력이 정렬되어 있지 않아도 정렬 단계를 따로 필요로 하지 않는다. 어느 쪽을 build 입력으로 삼는지와 메모리 한도를 고려해야 한다.
- 두 입력이 정렬되지 않았다면 병합 조인의 정렬 비용을 빼고 비교하면 안 된다. 반대로 이미 정렬된 데이터를 다시 정렬했다고 가정해서도 안 된다.
- 이 결과는 순수 Python 자료구조 구현의 한 측정이다. DBMS는 정렬·해시를 최적화하고, 디스크 spill·메모리 grant·병렬 실행·추가 정렬 요구까지 고려하므로 이 숫자로 PostgreSQL이나 MySQL의 실행 계획을 단정할 수 없다.
- 결과가 큰 join은 두 방식 모두 출력 크기에 비례한 메모리가 필요할 수 있다. 이 코드는 전체 결과를 리스트로 만들어 측정하므로, 스트리밍 소비자나 DB의 파이프라인 실행과는 다르다.
