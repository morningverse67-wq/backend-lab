# 015. 데드락 재현과 락 순서 고정

> 두 계좌 사이 이체 200건을 양방향으로 동시에 보냈다. 각자 순서대로 잠그면 데드락이 250번 나서 그때마다 롤백하고 다시 시도했다. 작은 id부터 잠그게 바꾸자 0번이 됐고, 전체 시간도 521.0ms에서 345.1ms로 줄었다.

## 문제

이체는 두 행을 바꾼다. 보내는 계좌를 먼저 잠그고, 받는 계좌를 나중에 잠그는 코드가 흔하다.

```sql
-- 트랜잭션 1: A -> B             -- 트랜잭션 2: B -> A
UPDATE accounts SET balance = balance - 10 WHERE id = 'A';   -- A 잠금
                                  UPDATE accounts SET balance = balance - 10 WHERE id = 'B';   -- B 잠금
UPDATE accounts SET balance = balance + 10 WHERE id = 'B';   -- B를 기다림
                                  UPDATE accounts SET balance = balance + 10 WHERE id = 'A';   -- A를 기다림 → 서로 영원히 기다림
```

둘 다 상대가 쥔 행을 기다리니 혼자서는 끝나지 않는다. DB는 둘 중 하나를 롤백해서 끊는다. InnoDB는 기다림이 사이클을 이루는지 바로 검사해서(데드락 감지) 한쪽을 롤백하고, 감지를 끄면(`innodb_deadlock_detect = OFF`) 잠금 대기 타임아웃(`innodb_lock_wait_timeout`, 기본 50초)이 지나야 끊긴다. 어느 쪽이든 롤백된 트랜잭션은 처음부터 다시 해야 한다.

## 실험

- SQLite 파일 DB(WAL)에 `accounts(id, balance)` 테이블
- 1부, SQLite에서 그대로: 연결 두 개, `busy_timeout = 5000`. SQLite는 행 잠금이 없고 쓰기 잠금이 파일 하나에 하나라서, 데드락은 "둘 다 읽기 트랜잭션을 연 뒤 둘 다 쓰려는" 모양으로 나온다. 이때 걸리는 시간과, `BEGIN IMMEDIATE`로 쓰기 잠금을 먼저 잡았을 때를 비교
- 2부, 행 잠금 이체: 4스레드 x 이체 50건 = 200건. 행 잠금은 Python으로 흉내 냈다(행마다 도착 순서대로 넘겨주는 배타 잠금). 첫 행을 잠그고 1ms 작업(두 UPDATE 문장 사이의 시간), 두 번째 행을 잠근 뒤 두 행을 SQLite 트랜잭션 하나로 쓴다. 롤백되면 잠근 행을 풀고 0~2ms 쉬었다가 다시 시도
  - 순서 없음 + 타임아웃: 잠금을 30ms 기다려도 못 얻으면 롤백 (데드락 감지가 없을 때. 실행 시간을 줄이려고 타임아웃을 짧게 잡았다)
  - 순서 없음 + 데드락 감지: 기다리기 전에 "누가 누구를 기다리는지" 그래프를 따라가서, 내가 기다리면 사이클이 되면 바로 롤백 (InnoDB 기본 동작을 흉내. 롤백할 쪽은 기다리려던 트랜잭션으로 정했고, InnoDB는 바꾼 행이 적은 트랜잭션을 고른다)
  - 순서 고정: 보내는 쪽/받는 쪽과 상관없이 id가 작은 계좌부터 잠금
- 계좌 2개(모든 이체가 같은 두 행을 양방향으로)와 계좌 1,000개(임의의 두 계좌)에서 같은 이체 목록으로 비교. 3번 돌려 지표별 중앙값
- 세 방식 모두 계좌별 최종 잔액이 이체 목록으로 계산한 값과 같고 합계가 그대로인지, 순서 고정은 데드락·타임아웃이 0번인지 `assert`로 확인

```bash
python3 main.py
```

## 배운 점

- 데드락은 잠그는 순서가 서로 반대일 때 생긴다. 계좌 2개에서 순서 없이 잠그면 이체 200건에 데드락이 250번 났다. 롤백된 이체가 다시 시도하다 또 걸리기도 해서 이체 건수보다 많다. 결과는 세 방식 모두 같았다. 데드락은 데이터를 깨뜨리지 않고 시간과 재시도를 쓴다.
- 데드락 감지가 있으면 피해가 작다. 사이클이 생기는 순간 한쪽을 롤백하니 전체 시간은 521.0ms였다. 감지 없이 타임아웃만 기다리면 서로 묶인 두 이체가 30ms씩 버티는 동안 뒤의 이체도 줄줄이 타임아웃(443번)에 걸려 6,658.9ms, 감지 방식의 12.8배가 됐다. 타임아웃 하나로는 데드락과 그냥 긴 대기를 구분하지도 못한다.
- 잠그는 순서를 하나로 정하면 사이클 자체가 안 생긴다. id 작은 계좌부터 잠그자 데드락 0번, 전체 시간 345.1ms(감지보다 1.51배 빠름), p99가 46.42ms에서 7.37ms가 됐다. 재시도를 처리하는 코드가 없어도 된다.
- 대신 항상 이득은 아니다. 계좌가 1,000개로 흩어지면 같은 두 행을 반대로 잡을 일이 거의 없어서 세 방식 모두 데드락 0번, 시간도 80.2~82.2ms로 같았다. 또 순서 고정은 잠글 행을 처음부터 알아야 쓸 수 있다. 첫 행을 읽어야 다음에 잠글 행이 정해지는 흐름이면 순서를 못 정하니, 데드락이 나면 트랜잭션 전체를 다시 시도하는 코드가 여전히 필요하다. SQLite처럼 쓰기 잠금이 하나뿐이면 `BEGIN IMMEDIATE`로 쓰기 잠금을 먼저 잡는 쪽이 같은 역할을 한다. 1부에서 둘 다 읽은 뒤 쓰려 하자 SQLite는 `busy_timeout`을 기다리지 않고 0.005ms 만에 실패를 돌려줬고(기다려도 풀리지 않을 상황이면 바로 `SQLITE_BUSY`를 준다고 문서에 나온다), `BEGIN IMMEDIATE`에서는 B가 실패하지 않고 기다렸다.
