# 013. 격리 수준 현상, 직접 만들어 보면 무엇이 보일까

> 계좌 A와 B의 합은 항상 2,000이다. 그런데 A를 읽고 0.2ms 뒤에 B를 읽는 합계 보고서 1,000건 중 235건이 2,000이 아닌 값을 보여 줬다. 두 번의 읽기를 읽기 트랜잭션 하나로 묶자 0건이 됐다.

## 문제

격리 수준 질문에는 보통 표 하나로 답한다. READ UNCOMMITTED는 dirty read, READ COMMITTED는 non-repeatable read, REPEATABLE READ는 phantom read가 생길 수 있다는 식이다.
표는 외우기 쉽지만 실제로 어떤 값이 보이는지, 서비스에서는 어떤 모습으로 나타나는지는 잘 안 보인다.

```sql
-- 합계 보고서: 두 문장이 각각 다른 시점의 데이터를 볼 수 있다
SELECT balance FROM accounts WHERE id = 1;   -- A
SELECT balance FROM accounts WHERE id = 2;   -- B (그 사이에 이체가 커밋되면?)
```

이번 lab은 SQLite 연결 두 개로 세 현상을 순서대로 재현하고, 같은 일이 동시에 일어날 때 얼마나 자주 틀리는지, 그리고 막는 대신 무엇을 내는지 잰다.

## 실험

- SQLite 파일 DB(WAL 모드). SQLite는 MySQL처럼 격리 수준을 고르는 옵션이 없어서, 아래 두 읽기 방식을 비교한다
  - 자동 커밋 읽기: 문장마다 그때 최신 커밋을 본다. 한 트랜잭션 안에서 문장마다 새 스냅샷을 보는 READ COMMITTED와 비슷한 모습
  - 읽기 트랜잭션 하나: `BEGIN` ... `COMMIT` 안에서 읽는다. 첫 읽기 때 잡은 스냅샷을 끝까지 본다
- 1부, 단계별 재현: 연결 하나가 두 번 읽고, 그 사이에 다른 연결이 커밋한다
  - dirty read: 다른 연결이 잔액을 0으로 바꾸고 커밋하지 않은 채 읽은 뒤 `ROLLBACK`. 공유 캐시 + `PRAGMA read_uncommitted = 1`(SQLite에서 커밋 안 된 값을 볼 수 있는 유일한 방법), 공유 캐시 기본값, 일반 연결을 비교
  - non-repeatable read: 같은 행을 두 번 읽는 사이에 `UPDATE` 커밋
  - phantom read: `COUNT(*) WHERE amount >= 100`을 두 번 하는 사이에 조건에 맞는 행 `INSERT` 커밋
  - 스냅샷 위에 쓰기: 읽기 트랜잭션에서 읽은 뒤 다른 연결이 커밋하고, 그다음 `UPDATE`
- 2부, 동시 실행: 쓰기 스레드 1개가 약 1ms마다 A와 B 사이에서 1~100을 옮긴다(트랜잭션 하나로 커밋). 읽기 스레드 4개가 보고서 250건씩, A를 읽고 0.2ms 뒤 B를 읽는다. 3번 돌려 지표별 중앙값
- 3부, 대가: 읽기 트랜잭션 하나를 열어 둔 채 다른 연결이 작은 커밋 3,000번을 하면 WAL 파일이 얼마나 커지는지. 3번 돌려 중앙값
- 단계별 결과는 기대한 값과 같은지, 읽기 트랜잭션 보고서는 틀린 합계가 0건인지, 쓰기 쪽 합계는 항상 2,000인지 `assert`로 확인

```bash
python3 main.py
```

## 결과

![A를 읽고 0.2ms 뒤 B를 읽는 합계 보고서 1,000건 중 자동 커밋 읽기는 235건이 틀렸고 읽기 트랜잭션 하나로 묶으면 0건. 같은 행을 두 번 읽으면 1000에서 500으로, 범위 COUNT는 3에서 4로 바뀌었지만 읽기 트랜잭션 안에서는 그대로였다. 대신 읽기 트랜잭션을 열어 둔 채 커밋 3,000번을 하면 WAL 파일이 3.93MB에서 11.79MB로 3.0배 커진 비교 그래프](result.png)

1부: 단계별 재현 (두 번 읽는 사이에 다른 연결이 커밋)

| 현상 | 자동 커밋 읽기 | 읽기 트랜잭션 하나 | `COMMIT` 뒤 다시 읽기 |
|---|---|---|---|
| non-repeatable read (같은 행 두 번) | 1000 → 500 | 1000 → 1000 | 500 |
| phantom read (`COUNT(*)` 두 번) | 3 → 4 | 3 → 3 | 4 |

| dirty read (커밋 안 된 `balance = 0`, 이후 `ROLLBACK`) | 읽은 값 |
|---|---|
| 공유 캐시 + `read_uncommitted = 1` | 0 (끝내 커밋되지 않은 값, 최종 값은 1000) |
| 공유 캐시, 기본값 | 에러: `database table is locked: accounts` |
| 일반 연결 (WAL) | 1000 |

스냅샷 위에 쓰기: 읽기 트랜잭션에서 1000을 읽은 뒤 다른 연결이 500으로 커밋하고 `UPDATE`하면, `busy_timeout`을 10초로 줬는데도 0.007ms 만에 `database is locked` 에러가 났다. `ROLLBACK` 뒤 값은 500.

2부: 합계 보고서 (A + B는 항상 2,000, 읽기 스레드 4개 x 250건, 3회 실행의 지표별 중앙값)

| 읽기 방식 | 합계가 틀린 보고서 | 가장 크게 틀린 차이 | 보고서 1건 p50 (ms) | 그동안 이체 수 |
|---|---:|---:|---:|---:|
| 자동 커밋 읽기 | 235 / 1,000 | 98 | 0.315 | 60 |
| 읽기 트랜잭션 하나 | 0 / 1,000 | 0 | 0.314 | 61 |

3부: 작은 커밋 3,000번 뒤 WAL 파일 크기 (3회 실행의 중앙값)

| 조건 | WAL 크기 | 쓰기 3,000번 시간 (ms) |
|---|---:|---:|
| 열린 읽기 없음 | 3.93MB | 81.6 |
| 읽기 트랜잭션을 열어 둠 | 11.79MB (3.0배) | 164.8 |

<sub>Python 3.13 / SQLite 3.50, 파일 DB(WAL, synchronous=NORMAL). 2부 3회 값: 자동 커밋 읽기의 틀린 보고서 235 / 187 / 235건, 읽기 트랜잭션 0 / 0 / 0건. 3부 WAL 크기는 3회 모두 같았고, 쓰기 시간 차이는 실행할 때마다 1.5~2.0배 사이로 흔들렸다. 스레드 실행 순서에 따라 매번 조금씩 달라지고, 환경에 따라 수치는 달라질 수 있음.</sub>

## 배운 점

- 격리 수준 현상은 버그처럼 에러가 나지 않는다. 자동 커밋으로 A와 B를 따로 읽은 보고서는 1,000건 중 235건이 합계를 틀렸고 가장 크게는 98이 어긋났다. 두 문장 사이에 이체가 커밋됐을 뿐, 어느 쪽 코드도 틀리지 않았다. 여러 값을 같은 시점 기준으로 맞춰 봐야 하는 조회(합계, 정산, 통계)에서 문제가 된다.
- 읽기 트랜잭션 하나로 묶으면 0건이 됐고, 보고서 1건 p50은 0.315ms vs 0.314ms로 사실상 같았다. 같은 행을 다시 읽어도(1000 → 1000), 범위를 다시 세어도(3 → 3) 처음 본 스냅샷 그대로였다. 대신 그 사이 커밋은 `COMMIT` 뒤에야 보인다. "최신 값"이 필요한 화면에 오래 연 트랜잭션은 맞지 않는다.
- 스냅샷을 오래 붙잡으면 대가가 있다. 읽기 트랜잭션 하나를 열어 둔 채 커밋 3,000번을 하자 WAL 파일이 3.93MB에서 11.79MB로 3.0배 커졌다. 열린 스냅샷이 아직 봐야 하는 옛 내용을 덮어쓸 수 없으니 체크포인트가 WAL을 비우지 못하고, WAL을 처음부터 다시 쓰지 못해 계속 늘어난 것이다. 이 실행에서 쓰기 시간도 81.6ms에서 164.8ms로 늘었다(실행마다 1.5~2.0배). 긴 배치나 커밋 없이 놀고 있는 연결이 있으면 이런 일이 생긴다.
- 스냅샷은 읽기만 지켜 준다. 읽기 트랜잭션에서 1000을 읽고 다른 연결이 500으로 바꾼 뒤 쓰려고 하면, SQLite는 기다리지 않고 0.007ms 만에 실패시켰다. 옛 값으로 계산해 덮어쓰는 걸 막는 대신 재시도는 앱이 해야 한다. 나중에 쓸 트랜잭션이면 처음부터 `BEGIN IMMEDIATE`로 쓰기 락을 잡는 편이 낫다. MySQL InnoDB의 REPEATABLE READ는 여기서 다르게 동작한다고 문서에 나와 있다. 일반 `SELECT`는 스냅샷을 읽지만 `UPDATE`는 가장 최근 커밋을 읽는다([lab 012](../012-stock-decrement-concurrency)의 원자적 UPDATE가 그래서 안전하다). 이 lab은 SQLite만 쟀고 MySQL·PostgreSQL의 격리 수준별 동작은 직접 재지 않았다.
