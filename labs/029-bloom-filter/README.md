# 029. Bloom filter로 존재 여부 빠르게 거르기

> 키 10만 개를 125KB짜리 Bloom filter(키당 10비트)에 넣자, 90%가 없는 키인 조회 10만 건 중 저장소까지 간 조회가 100,000건에서 10,728건으로 줄었다. 오탐률은 0.84%로 공식(0.82%)과 거의 같았고, 있는 키를 없다고 한 경우는 0건이었다. 대신 계획보다 2배를 넣자 오탐률이 13.88%로 올랐고, 키 100개를 지우려고 비트를 0으로 되돌리자 남은 키 486개가 '없음'으로 나왔다.

## 문제

아이디 중복 확인, 없는 상품 ID로 들어오는 요청, 캐시에 없는 키가 계속 DB로 가는 경우(cache penetration)처럼 **"없는 키"를 묻는 조회**가 많으면, 답이 "없음"인데도 매번 저장소까지 간다.

Bloom filter는 비트 배열 하나로 "확실히 없음" 또는 "있을 수도 있음"만 답한다. 있을 수도 있을 때만 저장소에 물으면 된다.

```python
if user_id not in bloom:     # 확실히 없음 → 저장소에 안 감
    return None
return store.get(user_id)    # 있을 수도 있음 → 실제 확인
```

얼마나 작고, 얼마나 거르고, 어디서 틀리는지 잰다.

## 실험

- 저장소에 있는 사용자 ID 10만 개, 조회 10만 건(있는 키 10%, 없는 키 90%), 시드 고정
- 비트 배열은 `bytearray`, 해시는 `hashlib.blake2b` 128비트 하나를 둘로 나눈 double hashing(`h1 + i*h2`). 표준 라이브러리만 사용
- 키당 비트 수(bits/key)를 4, 8, 10, 16으로 바꾸고, 해시 개수 k는 `round(bits/key × ln 2)`
- 오탐률: 넣지 않은 키 5만 개로 측정하고 공식 `(1 - e^(-kn/m))^k`와 비교
- 저장소 조회 수: 필터가 "있을 수도 있음"이라고 답한 조회 수
- 비교 대상: 같은 키를 담은 Python `set`(문자열 자체는 빼고 해시 테이블만, `tracemalloc`)
- 한계 두 가지: 10만 건 기준 크기에 20만~40만 건을 넣기, 키 100개의 비트를 0으로 되돌려 "삭제"하기

```bash
python3 main.py
```

## 결과

bits/key 별 (키 10만 개, 조회 10만 건 중 실제로 있는 키 10,000건)

| bits/key | k | 필터 크기 | 오탐률 측정 | 오탐률 공식 | 저장소 조회 | 있는 키를 없다고 함 |
|---:|---:|---:|---:|---:|---:|---:|
| 필터 없음 | - | - | - | - | 100,000 | - |
| 4 | 3 | 50.0KB | 14.77% | 14.69% | 23,259 | 0 |
| 8 | 6 | 100.0KB | 2.26% | 2.16% | 12,005 | 0 |
| 10 | 7 | 125.0KB | 0.84% | 0.82% | 10,728 | 0 |
| 16 | 11 | 200.0KB | 0.03% | 0.05% | 10,045 | 0 |

같은 키 10만 개를 담은 Python `set`의 해시 테이블은 4.19MB(문자열 제외). 10 bits/key 필터(125KB)의 약 34배다.

예상보다 많이 넣으면 (10 bits/key, 10만 건 기준 크기 그대로)

| 넣은 키 | 오탐률 측정 | 오탐률 공식 |
|---:|---:|---:|
| 100,000 | 0.84% | 0.82% |
| 200,000 | 13.88% | 13.78% |
| 300,000 | 40.18% | 40.08% |
| 400,000 | 64.54% | 64.46% |

키 100개의 비트를 0으로 되돌려 "삭제"하면

```text
100개 키 비트 제거 → 남은 99,900개 중 '없음'으로 잘못 나온 키 486개 (false negative)
```

조회 10만 건 시간은 이 Python 구현에서 `set` 3.2ms, Bloom filter 91.6ms였다(다시 돌린 실행에서는 1.8ms, 84.4ms).

<sub>Python 3.13.12, macOS arm64. KB·MB는 1,000 / 1,000,000바이트. 시간은 5회 중 최소값이고 실행마다 달라짐. 오탐률·조회 수는 시드 고정이라 같은 환경에서 매번 같음.</sub>

## 배운 점

- Bloom filter가 줄여 주는 것은 **없는 키에 대한 저장소 조회**다. 있는 키 10,000건은 필터가 있어도 그대로 저장소에 가고, 줄어드는 것은 없는 키 90,000건 중 오탐을 뺀 나머지다. 없는 키 조회가 적은 서비스라면 얻을 것도 적다.
- 크기는 키 길이와 상관없이 bits/key로 정해진다. 10비트(키당 1.25바이트)에 오탐률 약 1%, 16비트에 0.03~0.05%. 측정값이 공식과 0.1%p 안에서 맞아서, 크기는 "예상 키 수 × 원하는 오탐률"로 미리 계산할 수 있다.
- 대신 그 **예상 키 수가 틀리면 조용히 나빠진다.** 2배를 넣자 오탐률이 0.84% → 13.88%, 4배면 64.54%였다. 에러는 나지 않고 저장소 조회만 늘어난다. 키가 늘어나는 데이터라면 다시 만들 시점이나 크기를 늘리는 방식을 정해 둬야 한다.
- 일반 Bloom filter는 **지울 수 없다.** 비트 하나를 여러 키가 같이 쓰기 때문에, 100개를 지우려고 비트를 끄자 상관없는 키 486개가 "없음"이 됐다. "없음"을 믿고 저장소에 안 가는 구조에서 이건 데이터가 사라진 것처럼 보이는 버그다. 삭제가 필요하면 카운터를 쓰는 변형(counting Bloom filter)이나 주기적 재생성을 쓴다.
- 이 실험은 Python으로 구현해서 조회 자체는 `set`보다 수십 배 느렸다. 메모리에 다 들어가는 키라면 `set`이 낫다. Bloom filter가 의미 있는 것은 키가 메모리에 다 안 들어가거나, 뒤에 있는 저장소 조회(디스크, 네트워크)가 필터 계산보다 훨씬 비쌀 때다.
